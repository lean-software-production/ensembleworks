# Multi-user browser terminals: the device-report fan-in problem

**Status:** field report + design guidance
**Date:** 2026-07-26
**Audience:** anyone building a shared/multiplayer terminal where several browser
terminal emulators are attached to one PTY
**Provenance:** everything below was measured on a running EnsembleWorks dev
stack (EW-3, PR #64; follow-up EW-3b, PR #65), not reasoned about in the
abstract. Captures are quoted verbatim.

---

## 1. The topology that creates the problem

A shared terminal is usually built like this:

```
   one PTY  ──► gateway ──► browser A (xterm.js)
   (shell,      (fan-out)   browser B (xterm.js)
    tmux, …)                browser C (xterm.js)

   one PTY  ◄── gateway ◄── all three browsers' input, merged
                (fan-in)
```

Fan-out is one-to-many: every byte the PTY produces is copied to every attached
client, so everyone sees the same screen. Fan-in is many-to-one: every byte any
client sends is written into the single PTY, so anyone can type.

Fan-in is correct for *typing*. The problem is that **keystrokes are not the
only thing a terminal emulator sends upstream**, and at the wire level the other
things are indistinguishable from typing.

## 2. The invariant being violated

> A terminal protocol assumes **exactly one entity speaks as the terminal**.

Terminal control is a two-way protocol. Programs ask the terminal about itself,
and the terminal answers *on the same channel the keyboard uses*. There is no
separate metadata channel, no framing that says "this is a report, not a
keypress", and no addressing.

Attach N emulators to one PTY and N entities now speak as the terminal. Every
query gets N answers. The program consumes one. The remaining N−1 have nowhere
to go but into whatever is reading the PTY next — usually the user's shell.

Everything in this document is a consequence of that one violated invariant.

## 3. What the browser sends upstream

Classify by *who generates it*, because that determines whether it may be
dropped:

| Class | Example | Generated by | Multi-client safe? |
|---|---|---|---|
| Keystrokes | `ls -la\r`, `\x03`, `\e[A` | the human | yes — N users typing is the point |
| Mouse reports | `\e[<0;10;20M` | the human's pointer | yes — genuine user input |
| Bracketed paste | `\e[200~…\e[201~` | the human's clipboard | yes |
| **Device reports** | `\e[?1;2c`, `\e]11;rgb:…` | **the emulator, automatically** | **no — N copies of one answer** |
| Focus events | `\e[I` / `\e[O` | the emulator, per-viewer | no — "focus" is meaningless when shared |

Only the last two categories are problematic, and only because they are
*automatic*. The emulator generates them with no human involvement, so N
emulators generate N of them for one stimulus.

### The device reports you will actually meet

| Report | Reply shape | What asks for it |
|---|---|---|
| DA1 — primary device attributes | `\e[?1;2c` | terminal feature probes, tmux attach |
| DA2 — secondary device attributes | `\e[>0;276;0c` | version/identity detection |
| DA3 — tertiary device attributes | `\eP!\|…\e\\` | rare |
| CPR — cursor position report | `\e[24;80R` | size/inline detection, some prompts |
| DSR — device status report | `\e[?1;0n` | liveness checks |
| DECRPM — mode report | `\e[?2026;2$y` | capability detection (see §9) |
| XTVERSION | `\eP>\|tmux 3.5\e\\` | terminal identification |
| OSC 10/11 — fg/bg colour | `\e]11;rgb:ffff/ffff/ffff` | **light/dark theme detection** |
| OSC 4 — palette entry | `\e]4;0;rgb:0f0f/1717/2a2a` | palette-aware colour mapping |
| Kitty keyboard flags | `\e[?…u` | keyboard protocol negotiation |

## 4. Failure mode: surplus replies become shell input

With two browsers attached, this is what lands on the command line:

```
dev@b32aadc2db62:~$ 1;2c0;276;0c
```

That is DA1 (`\e[?1;2c`) plus DA2 (`\e[>0;276;0c`) with the `\e[?` / `\e[>`
introducers consumed as unrecognised control sequences, leaving the printable
payload as literal text. Read server-side from the PTY, not from the browser —
those bytes genuinely sat in the shell's input buffer.

Under load it looks like this (20 queries × 2 browsers):

```
dev@…$ 1;2c0;276;0c1;2c0;276;0c1;2c1;2c0;276;0c1;2c0;276;0c1;2c0;276;0c…
```

And with a newline behind it, the shell does the obvious thing:

```
-bash: 1: command not found
-bash: 2c0: command not found
-bash: 276: command not found
```

It also corrupts real commands. During testing, a queued burst of replies
shredded a command mid-flight so that `clear && cd … && opencode` reached the
shell as `0cclear: command not found`.

**Severity note for implementers:** this is an input-injection path. Bytes the
user never typed reach their shell, and can arrive interleaved with bytes they
did type. It is not merely cosmetic.

## 5. Amplification, and why "it only breaks with lots of people"

The bug is arithmetic, not load:

| Clients attached | Replies produced | Consumed by the asking program | Landing at the prompt |
|---|---|---|---|
| 1 | 1 | 1 | 0 — invisible |
| 2 | 2 | 1 | 1 |
| 6 | 6 | 1 | 5 |

One client is always clean, which is why this survives single-user development
and testing entirely. **Two clients is enough to reproduce.** Any test plan that
does not attach a second client will report success.

## 6. The three trigger paths

**(a) A query in the output stream.** Any program in the pane emitting a query
gets it broadcast to all N clients; all N answer.

**(b) Scrollback replay on attach.** This is the subtle one. A gateway normally
keeps a rolling buffer of recent PTY output and replays it to newly attached
clients so their screen isn't blank:

```ts
const SCROLLBACK_LIMIT = 256 * 1024 // bytes replayed to newly attached clients

ws.send(JSON.stringify(attachedMsg))
if (session.scrollback.length > 0) {
	ws.send(Buffer.concat(session.scrollback), { binary: true })   // ← replay
}
session.clients.add(ws)
```

That buffer holds **raw bytes**, escape sequences included — it must, because
that is what paints the screen. So any query that ever passed through the pane
is still in there, and gets re-asked of every fresh emulator. The new client
answers a question from ten minutes ago, and its answer fans into everyone's
shell.

Consequence: **every reload, every reconnect, and every late joiner re-triggers
the bug with nobody touching a keyboard.** In our repro, simply opening a second
tab was sufficient.

**(c) Multiplexer probes.** If there is a terminal multiplexer in the stack, it
probes its outer terminal at attach time (fg/bg colour, DA). Those probes reach
all N clients too.

## 7. The fix we shipped, and what it bought

**Approach A — filter device reports at the single PTY-write chokepoint.**

Every client's input converges on one line, which makes the guard a one-liner:

```ts
// before
session.pty.write(msg.data)

// after
session.pty.write(stripTerminalReports(msg.data))
```

`stripTerminalReports` is pure and dependency-free: a list of targeted regexes,
applied per-occurrence, removing one class of report each. Deliberately *not* a
broad "strip all CSI" rule, so mouse reports and bracketed paste cannot be
caught by accident. Roughly:

```ts
const REPORT_PATTERNS: RegExp[] = [
	/\x1b\[\?[0-9;]*c/g,                    // DA1
	/\x1b\[>[0-9;]*c/g,                     // DA2
	/\x1bP!\|[0-9A-Fa-f]*\x1b\\/g,          // DA3
	/\x1b\[(?!1;[2-8]R)[0-9;]*R/g,          // CPR — see §8 for the lookahead
	/\x1b\[\?[0-9;]*n/g,                    // DSR
	/\x1b\[\?[0-9;]*\$y/g,                  // DECRPM
	/\x1bP>\|[^\x1b]*\x1b\\/g,              // XTVERSION
]
```

**What it fixed, measured:** with the filter in place and two clients attached,
both triggers go completely silent. 20 forced DA queries produced zero bytes at
the prompt, where the unfixed build produced ~40 replies and a wall of garbage.
Reload/late-join injection stopped too.

**Why it was attractive:** one place, no protocol change, no client rebuild,
covers every client implementation at once, and unit-testable as a pure
function.

**Why it was safe *in our stack specifically*:** tmux sat between the browsers
and the shell and answered programs' queries itself, from its own emulator
state, with capabilities pinned in config rather than probed outward. So the
browsers' replies were surplus by construction. **This premise is
load-bearing** — see §11.

## 8. First warning sign: reply shapes collide with real keystrokes

The CPR pattern above carries a negative lookahead, and the reason generalises.

A cursor-position report is `CSI <row> ; <col> R`. xterm.js encodes **modified
F3** as `CSI 1 ; <mod> R` — the *same shape*. A naive CPR filter silently eats
Shift-F3, Ctrl-F3, and friends.

The lookahead `(?!1;[2-8]R)` spares modifier codes 2–8, at the cost of leaking a
genuine cursor report for row 1, columns 2–8. That is the correct trade —
leaking a rare report beats silently eating a keystroke — but note what it
demonstrates:

> The wire format is ambiguous. There exist byte sequences that are *both* a
> valid device report and a valid keystroke. No content-based filter can be
> fully correct, because the information needed to disambiguate (did a human
> press a key?) does not exist in the bytes.

This is the first structural argument against filtering. §10 has the second.

## 9. Where the filter caused a new problem

The filter also stripped OSC colour reports. That broke every TUI that adapts to
the terminal's background.

**Case study — opencode.** In a canvas terminal (white background), opencode
rendered its **dark** theme variant, and continued to do so even when a light
theme was explicitly selected. Instrumenting both directions of the gateway
matched the query to the reply we were eating:

```
OUT-OSC/DCS "\e]11;?"                        ← opencode asks: what is your background?
STRIPPED    "\e]11;rgb:ffff/ffff/ffff"  ×4   ← the browser answers "white". Filter eats it.
```

With no answer, opencode kept its dark assumption. Confirmed by capturing the
painted background codes (`tmux capture-pane -pe`) for the same theme:

| build | background SGR codes |
|---|---|
| unfixed baseline | `48;5;15` (white) ×16, 255, 253, 252 — light |
| with the filter | `48;5;236` (dark grey) ×16, 60, 240, 23 — dark |

Identical layout and counts; only the palette differs. Commenting out that one
pattern flipped the rendering back and forth on demand.

Nothing else supplies this information — there is no environment variable, and a
multiplexer does not synthesize a background colour. **Drop the OSC reply and
light/dark detection is simply gone.**

### The discriminator we found: does the surplus *echo*?

Testing each class empirically produced a clean rule:

- **DA1 / DA2 / DECRPM payloads are printable.** `1;2c`, `0;276;0c`,
  `2026;2$y` — the introducer is consumed, the payload lands as text. Surplus
  copies are visible garbage.
- **OSC replies are wrapped.** `\e]` … terminated by ST or BEL. Readline
  consumes the whole sequence. Surplus copies are invisible.

Verified directly — ten OSC 10/11 queries fired at two attached browsers with
replies passing through:

```
dev@…$ bash /tmp/osc.sh
dev@…$
```

Clean prompt. Whereas the same test with DECRPM:

```
dev@…$ bash /tmp/decrqm.sh
dev@…$ 2026;2$y2004;1$y2026;2$y2004;1$y2026;2$y2004;1$y…
```

### The resulting matrix

| Report class | Surplus echoes as garbage? | Apps need the answer? | Filter verdict |
|---|---|---|---|
| DA1, DA2, DA3 | yes | no (multiplexer answers) | strip |
| CPR / DSR | yes | rarely | strip, with the F3 carve-out |
| XTVERSION | yes | some | strip (accepted loss) |
| **OSC 10/11/4** | **no** | **yes — light/dark, palette** | **do not strip** |
| DECRPM | yes | **yes — capabilities** | **genuine conflict, see below** |

We shipped the OSC row as a follow-up fix (PR #65). The DECRPM row is the one a
filter cannot resolve.

### The unresolved conflict: DECRPM

DECRPM is the reply half of private-mode feature detection:

```
app → terminal   CSI ? 2026 $ p        "mode 2026, status?"
terminal → app   CSI ? 2026 ; 2 $ y    "recognised, currently off"
```

State `0` means *not recognised* (unsupported); `1`/`2` mean supported. It is how
an app distinguishes a capable terminal from an incapable one. Our browsers
answered, truthfully and usefully:

| reply | mode | meaning |
|---|---|---|
| `\e[?2026;2$y` | synchronized output | supported |
| `\e[?2004;1$y` | bracketed paste | supported, on |
| `\e[?1004;1$y` | focus reporting | supported, on |
| `\e[?1016;2$y` | SGR-pixel mouse | supported |
| `\e[?2027;0$y` | grapheme clustering | not supported |
| `\e[?2031;0$y` | colour-scheme notifications | not supported |

All six discarded. Potential costs, in descending severity:

- **2004, bracketed paste** — without it a multi-line paste can be read as
  keystrokes-with-Enters, i.e. lines executing as they arrive.
- **2026, synchronized output** — frames no longer painted atomically; tearing
  and flicker on full redraws.
- **1004, focus reporting** — cosmetic.

Caveat we did **not** resolve: an app receiving no answer does not necessarily
disable the feature — many set modes unconditionally, and a multiplexer may
handle paste bracketing itself. The costs above are *possible*, not *measured*.
Measuring them is outstanding work.

## 10. Why filtering is the wrong layer

Two independent structural arguments:

1. **The gateway has the least information.** It sees an undifferentiated byte
   stream and must *guess* whether `\e[?1;2c` was auto-generated or typed. The
   browser has no such problem: xterm.js knows exactly which bytes it
   synthesized versus which came from a keypress. We put the classification
   where the evidence isn't.

2. **The set is open-ended.** Every terminal feature added since 1978 brings new
   sequences — 2026, 2031, kitty keyboard, sixel, and whatever lands next. Each
   one is a fresh coin flip between "echoes as garbage" and "an app needed it",
   discovered in production. We shipped one filter and it immediately broke a
   real application in a way nobody predicted.

A filter is a reasonable *stopgap*. It should not be the architecture.

## 11. If you remove the multiplexer, filtering collapses entirely

Worth stating plainly, because it is easy to miss: in our stack **tmux is what
answers programs' queries**. The browsers' replies were surplus *because
something else was already authoritative*.

Take tmux out — which several implementations will want to, for a leaner stack —
and under a filtering design **nothing answers anything**. Every app in every
terminal falls back to defaults, permanently. Filtering only appears viable
while an authoritative emulator is hiding in the middle of your stack.

## 12. Recommended architectures

### Option 1 — suppress at source, answer from the server *(recommended)*

1. **No browser ever speaks as the terminal.** Register handlers in xterm.js for
   the query sequences so the emulator never generates a reply, e.g.
   `term.parser.registerCsiHandler({ final: 'c' }, () => true)` (returning
   `true` marks the sequence handled and suppresses the default). Equivalents
   exist for OSC (`registerOscHandler`) and DCS (`registerDcsHandler`). Verify
   the exact contract against your xterm.js version.
2. **The gateway is the terminal.** It answers a defined set of queries with one
   pinned capability profile — your product's declared terminal identity.
   Unknown queries go unanswered, exactly as they do today.

Why this is the right shape:

- Zero input filtering anywhere. The phrase "which sequences do we strip"
  disappears from the codebase.
- Deterministic: every client gets identical answers regardless of browser,
  version, or platform.
- The profile is *knowable* — you ship the client, so you know what it supports,
  and it can be asserted in tests.
- Works identically with tmux, without tmux, or with any other multiplexer.
- Answers become correct rather than merely absent, so DECRPM capability
  detection (§9) is restored instead of accepted as a loss.

Note this is **not** the client-side regex-scrubbing of `onData` that gets
rejected in design reviews. It is telling the emulator not to produce the reply,
which is a much smaller and more reliable thing.

Costs: you must own a capability profile and keep it honest; a client that
somehow skips suppression re-introduces the bug (defend with a server-side
filter as belt-and-braces, or by rejecting unknown client versions).

### Option 2 — elect one responder

One attached client is designated primary and answers; all others suppress.
Preserves real per-browser capabilities. Costs: election, failover on
disconnect, and an awkward question when clients genuinely differ (Chrome on
Linux vs Safari on iPad — whose capabilities are "the terminal's"?). More moving
parts for a benefit you probably don't need if you ship the client.

### Option 3 — reply de-duplication in the gateway

Watch outbound for queries, admit the first matching inbound reply, drop the
rest until the next query. No client change required, and it preserves DECRPM.
But it still has to recognise reply shapes, so §8 and §10 apply — the
whack-a-mole is bounded, not eliminated. Reasonable if you cannot change the
client.

### Comparison

| | Client change | Filtering needed | Survives multiplexer removal | Restores capabilities | Complexity |
|---|---|---|---|---|---|
| Filter only (what we shipped) | no | **yes, unbounded** | **no** | no | low |
| 1. Suppress + server profile | yes | no | yes | yes | medium |
| 2. Elect a responder | yes | no | yes | yes | medium-high |
| 3. Gateway de-dupe | no | yes, bounded | yes | yes | medium |

## 13. The pattern to copy: authoritative resize

Our gateway already solves the identical problem correctly elsewhere, which is a
useful sanity check on the design above. N clients have N window sizes. Rather
than letting the last writer win, the gateway sets the PTY size and then
**broadcasts the authoritative size back to every client**, which all converge on
it:

```ts
function resizeSession(session: TermSession, cols: number, rows: number) {
	if (!session.pty.resize(cols, rows)) return
	const resizeMsg: TermServerMessage = { type: 'resize', cols: session.pty.cols, rows: session.pty.rows }
	const msg = JSON.stringify(resizeMsg)
	for (const ws of session.clients) if (ws.readyState === ws.OPEN) ws.send(msg)
}
```

Single authority, clients are renderers. Device reports should work the same
way. The asymmetry — resize done right, device reports left to fan in — is
exactly where the bug lived.

## 14. Checklist for implementers

- **Test with two clients from day one.** One client never reproduces this. Put
  a two-client attach in the automated suite, not just in the manual plan.
- **Decide who is the terminal, explicitly, in writing.** If the answer is "the
  browsers", you have this bug.
- **Treat scrollback replay as a re-trigger surface**, not just a paint
  convenience. Consider stripping *queries* from the replay buffer — filtering
  outbound queries to fresh clients is far safer than filtering inbound replies,
  because a query has no keystroke ambiguity.
- **Never filter on a shape that a keystroke can also produce** without checking
  the collision set (§8). CPR vs modified F3 is the known one; assume there are
  others.
- **Instrument both directions before theorising.** Log what the PTY emits and
  what each client sends. Our root cause was invisible until query and reply
  were logged side by side, and two of our confident predictions (truecolor
  degradation, the dark default being caused by the fix) turned out to be wrong
  when measured.
- **Distinguish "echoes as garbage" from "app needed it"** for every sequence
  class you handle. They are independent axes, and only the combination tells
  you what to do.
- **Focus events (`\e[I` / `\e[O`) are per-viewer** and meaningless when shared.
  Decide deliberately; do not let N clients fan focus changes into one PTY.
- **Watch for input-integrity, not just cosmetics.** Surplus replies interleave
  with real typing and corrupt commands in flight.

## 15. Reproduction and verification recipes

**Setup:** one shared session, **two** browser clients attached.

**Trigger B — natural.** Open a second tab, or hard-reload one. Scrollback replay
re-asks any query in the buffer. No typing required.

**Trigger A — deterministic.** Push a query out to every client. Under tmux this
needs passthrough (`allow-passthrough on`), doubling the inner ESC:

```sh
for i in $(seq 1 10); do
  printf '\033Ptmux;\033\033[c\033\\'      # each browser replies \e[?1;2c
  printf '\033Ptmux;\033\033[>c\033\\'     # each browser replies \e[>0;276;0c
done
```

**Read the PTY, not the browser.** `tmux capture-pane -p -t <session>` shows what
actually reached the shell, which settles "is this a rendering artifact?"
immediately.

**Inspect painted colours** with `tmux capture-pane -pe` and grep for `48;` (background)
and `38;` (foreground) SGR codes. This is how the theme regression was proven
objectively rather than by eye.

**Instrument the gateway** temporarily at both boundaries — log each outbound
query and each inbound sequence you drop, to a file rather than stdout (a live
log pane only holds one screenful and the interesting lines scroll away; this
cost us a full test cycle).

**Bisect one pattern at a time.** Disable exactly one filter rule, re-run,
observe. That is what isolated OSC 11 as the sole cause of the theme regression.

## 16. Open questions

- Does losing DECRPM `2004` actually break bracketed paste in practice, or do
  apps/multiplexers set it unconditionally? Unmeasured.
- Does losing `2026` cause visible flicker in a busy TUI? Unmeasured.
- What belongs in a pinned server-side capability profile, and how is it kept
  honest against the client's real abilities as xterm.js evolves?
- Should the *query* be stripped from the scrollback replay buffer as a
  belt-and-braces measure, independent of the chosen architecture?
