EnsembleWorks · Architecture proposal

A shared place to think,
talk, and build software.

A collection of BB plugins: a visual workspace, a conversation library, team presence, remote execution locations, and a software factory. Each owns a coherent domain; BB brings people and agents together.

01 / Technical foundations

Build on BB and the existing canvas engine.

BB supplies the application and agent environment. Loro supplies concurrent document editing. The existing canvas libraries turn that into an interactive visual workspace. These are technical foundations, not separate products to install.

The clean-room libraries remain canvas-model, canvas-doc, canvas-sync, and canvas-editor, with canvas-react as the thin DOM renderer. They are code boundaries consumed by Canvas.

Use CRDT documents for shared editing, expiring awareness for presence, database records for transcripts, and authoritative execution state for factory runs.
02 / Product domains

Plugin boundaries follow useful capabilities.

A plugin should be independently useful and own its configuration, storage, lifecycle, and failure handling. A source adapter or editor module does not automatically need to become a plugin.

Domains cooperate through stable references and explicit operations. A Canvas note can refer to a conversation, a BB thread, or eventually a factory run. BB remains authoritative for its threads, agents, environments, and message dispatch.

03 / Communications domain

One conversation library, multiple sources.

Bring the existing Communications Hub into plugins/communications-hub, preserving its isolated npm package and lockfile. It replaces the previously proposed Transcript plugin. The hub owns conversations and retrieval; adapters translate source-specific inputs.

Hub and source responsibilities

The hub assigns source-independent conversation IDs. Several threads can attach to one conversation, each with its own acknowledged ingestion sequence. Reading does not implicitly advance a cursor. Detaching does not stop capture. Ingestion sequence orders retrieval so late passages remain discoverable.

The source integration owns credentials, protocol handling, worker configuration, retries, and capture controls. The hub records capture state and observed interruptions. Stop capture must dispatch to the correct source; the current implementation routes it to Zoom.

The existing TranscriptSink interface provides the starting point: ensure a conversation, append segments, and update capture state. The worker needs an authenticated, versioned ingestion boundary and stable source keys for retries. A shared repository lets both sides evolve together, but does not remove the process boundary.

LiveKit integration and migration

  • Bounded capture sessions. A persistent room is closer to the hub's future “space” concept. Start with explicit sessions; reconnects retain the same session identity. Avoid one endless transcript.
  • Honest timing. Canvas currently stores epoch timestamps and permits longer utterances. Define the conversion to source-relative timing, preserve what is known, and split passages deterministically to the hub's 2,000-character limit.
  • Continuity. Report interruptions and source speaker identity; deduplicate retries. Capture status must not imply missing speech was recovered.
  • Optional spatial context. Canvas may link conversations or contribute enrichment. Storing spatial metadata requires an explicit extension to the current hub schema.

Discord and other chat sources are later extensions. Their adapters must preserve message IDs, edits, replies, and provenance; immutable transcript segments alone are insufficient. Spaces and channel windows remain future concepts.

Transcripts are evidence, never authority to execute instructions. The current hub uses the BB instance as its access boundary; per-project and per-user transcript permissions and a retention policy are not implemented.
04 / Visual collaboration

A shared workspace, with awareness at the right scope.

Canvas owns rendering, editor tools, synchronization, and shape-to-thread bindings, including agent actions and status badges. LiveKit stays inside Canvas initially because spatial gain, speaker indicators, and placement are coupled to the editor. Moving transcript ownership does not require extracting AV first.

Presence starts with typing on existing-thread composers: emit on actual text changes, throttle to roughly one pulse per second, expire after roughly three seconds, and clear on blur, hide, submit, or unmount. Send no draft content or character counts. Aggregate tabs per person and exclude the local tab.

Later, move BB-wide whereabouts from Canvas into Presence once identity and visibility rules are settled. A shared composer may use Loro text and ephemeral selections, but final message dispatch remains a BB command. Generalize synchronization only when a second durable consumer needs it: document replication and awareness remain distinct primitives with separate scopes.

05 / Remote execution locations

Central collaboration, distributed coding.

The BB server machine hosts the central application and plugin services. Most agentic coding work runs on remote machines connected to BB: agent processes, repository checkouts, terminals, builds, tests, and factory execution. Local execution remains possible, but is not the default placement for heavy coding work.

Build on BB's machine and environment model

An execution location is a user-facing way to select where work happens: a BB machine together with a suitable project environment. It is not a second host identity or enrollment system. BB owns connected-machine identity, enrollment, project-source setup, environment association, and execution routing. A machine can serve more than one project; environments identify the concrete workspace used for a task.

The Execution Locations domain adds team conventions and, where needed, plugin capabilities for location selection, readiness, provisioning profiles, and resource lifecycle policy. Start with BB's existing machine and environment selection. Add a dedicated plugin only for functionality beyond those built-in controls; provider-specific provisioning can use BB's machine and environment extension points.

Execution rules

  • Make placement explicit. Associate work with a BB host and environment. A thread remains centrally discoverable while its agent runs remotely. Resolve paths and commands on that environment's machine.
  • Check readiness. A connected host is not necessarily ready: source checkout, tools, agent authentication, and factory installation may still be missing.
  • Handle disconnection as uncertainty. Display unavailable or interrupted status and reconcile the existing remote work on reconnect. Do not silently rerun it centrally or on another machine.
  • Preserve results deliberately. Working files and build outputs live in the execution environment. Keep central run references and define how durable artifacts are published before retiring disposable compute. A connection is not a backup.
  • Keep ordinary agents independent of the factory. BB threads can execute directly on remote environments. Factory delegation is an additional workflow, not the required path for every coding task.

Initial adoption should use persistent connected machines and explicit placement. Automated scheduling, capacity balancing, disposable hosts, and suspend/resume policies are later capabilities. Their cleanup rules must account for factory runs as well as BB threads before retiring compute.

06 / Software factory domain

Delegate execution from a BB thread.

A Software Factory plugin connects BB to an execution engine installed on a selected remote execution machine. The plugin backend remains on the central BB server; the engine runs alongside its workspaces remotely. Fabro is the initial candidate. This proposal defines the integration boundary; it does not assume particular Fabro APIs or execution guarantees have been verified.

A factory run is separate from the thread discussing it. Persist the originating thread, target BB host and environment, engine identity, and run identifier so restarted sessions can find existing work. Reconcile uncertain submission outcomes before retrying to avoid duplicate runs.

The adapter should expose real engine states and capabilities, including cancellation semantics and result locations. Completion does not automatically mean changes are approved, merged, or deployed; those are separate explicit actions.

The first integration should demonstrate one bounded request, an observable run, and returned changes and test evidence. Engine installation, credentials, isolation, supported commands, and reconnect behavior need investigation before implementation commitments.

Use BB identifiers as integration points where possible. Share typed schemas as libraries, never another plugin's database or private implementation. Cooperation needs small, bounded, versioned capabilities such as “append transcript segments” or “create a Canvas note.” Validate inputs and scope callers.

The original proposal identified no general typed plugin-to-plugin service bus. Check the installed SDK before choosing a runtime mechanism. Authenticated HTTP fits the external transcription worker; source modules inside the hub can call its typed sink directly.

Potential SDK improvements include authenticated person identity, scoped presence delivery, composer activity and collaboration hooks, and typed capability discovery. These are proposed extensions, not assumed APIs. Broadcast realtime alone is not a privacy boundary. Secrets, permissions, and execution authorization never become CRDT state.

08 / Development and distribution

One repository; independent plugin releases.

The monorepo is the development home. Each plugin keeps an isolated npm package and lockfile, outside the root Bun workspaces. Communications Hub moves here rather than remaining an external repository dependency.

ensembleworks/
  plugins/
    canvas/
    communications-hub/    ← import the existing codebase
    presence/
    software-factory/
    execution-locations/   ← if additional placement policy needs a plugin
    discord-bridge/
  canvas-model/  canvas-doc/  canvas-sync/
  canvas-editor/  canvas-react/
  transcriber/
  collaboration-protocols/ ← when shared contracts need it
  .bb/plugins.json        ← collection index

The collection manifest indexes plugins; it does not silently install a suite. Development instances use local path installs and the normal build/reload loop. A repository helper can install selected profiles using BB's existing commands.

Release and compatibility rules

  • Use a dedicated plugin release script from clean, synchronized main: verify, bump package and lockfile, commit, create an annotated prefixed tag, and push. Never move an existing tag.
  • Continue using deploy/release.sh for the legacy application. Plugin releases use a separate scripted workflow.
  • Declare honest BB and SDK engine ranges. Verify current declarations and test a clean managed Git install, not only local path installation.
  • Relative Canvas dependencies such as file:../../canvas-doc require the complete monorepo at the release commit. Verify that installation shape in CI. Publish or bundle shared libraries only when extraction or npm distribution requires it.
  • Runtime data lives in BB plugin storage. Keep migration history append-only and test upgrades. Reverting a plugin version does not automatically reverse database changes.
  • Stage releases before production. Test compatible source-contract versions when the worker and hub ship separately. Publishing a tag does not update an instance automatically.

Release checks include npm ci, typechecking, focused tests, applicable quality gates, bb plugin types --check, bb plugin build, and a clean Git-install smoke check. Canvas interaction changes still require the repository's interaction contracts and independent red-then-green evidence. Verify frontend cleanup, reconnect behavior, worker disposal, and storage migrations where affected.

Keep the catalog limited to approved stable ranges; staging can install exact prerelease tags. BB's activation fallback cannot guarantee rollback of semantic data changes. Separate plugins also do not eliminate aggregate bundle cost: measure Loro and LiveKit loading, and avoid adding them to domains that do not need them.

09 / Adoption and open decisions

Integrate existing capabilities, then expand.

This is a proposed adoption sequence, not a claim that the moves or integrations have happened.

  1. Establish the collection. Import Communications Hub, preserve package isolation, and add the collection manifest and development instructions.
  2. Connect live transcription. Define capture sessions and worker ingestion. Verify duplicates, timing, interruptions, persistence, and thread retrieval.
  3. Move transcript ownership. Export Canvas history through its owner and import it into the hub. Switch transcript entry points after verifying parity, including useful time-window retrieval. Preserve old data until migration is validated; avoid indefinite dual writes.
  4. Deliver Presence independently. Start with typing indicators, then move whereabouts after identity and visibility are settled.
  5. Establish remote execution. Use connected BB machines and project environments for ordinary coding threads. Verify placement, readiness, reconnect behavior, and result access before adding provisioning automation.
  6. Prove factory delegation. Investigate the engine interface and deliver one request-to-result flow on a selected remote environment, with durable run association and explicit controls.
  7. Make releases repeatable. Add release automation, clean Git-install CI, a catalog, and staging promotion before production adoption.
  8. Expand when needed. Discord workflows, chat-aware entries, Huddle extraction, and shared composer editing follow their required contracts.

Open decisions

  • LiveKit session boundaries and historical timing conversion.
  • Presence identity, scope, and visibility.
  • Hub retention and access controls beyond a trusted instance.
  • Execution-location selection, readiness, credentials, capacity, and artifact retention.
  • Which location capabilities need a plugin beyond BB's built-in machine controls.
  • Fabro's actual interface and execution isolation on a remote environment.
  • Stable-range promotion and production compatibility policy.
  • Whether shared drafting remains in Presence or becomes a separate product when justified.
Preserve narrow ownership: no universal CRDT, cross-plugin database access, automatic execution from speech, or automatic production upgrades. AV extraction is not a prerequisite for transcript integration.
